# CLAUDE.md

Backend for **SIMRS** (Hospital Information Management System), serving an admin dashboard.
These rules are mandatory. If a request conflicts with one, say so and ask before proceeding. Never break a rule silently.

## Stack

Go · Gin · GORM + PostgreSQL · JWT HS256 + bcrypt · swaggo (Swagger 2.0).
Go module name is `gin-quickstart`; every import starts with `gin-quickstart/...`.

## Commands

```bash
make run              # regenerate Swagger docs, then start the server
make swagger          # regenerate docs/ only
go build ./...        # compile
go vet ./...          # static checks
gofmt -l .            # must print nothing
go mod tidy           # after adding or removing a dependency
docker compose up -d --build   # deploy the API as a container (PostgreSQL and MinIO run outside Docker)
```

No test suite exists yet. When you add tests, use the standard `testing` package next to the code (`*_test.go`) and run `go test ./...`.

   - `gofmt -l .` is empty; `go vet ./...` and `go build ./...` pass.
   - `make swagger` succeeds if you touched a handler annotation, DTO, or route.
   - Behavior changes were exercised against a running server (see "Testing against a database").
4. **Report honestly.** Say what you tested, what you did not, and what failed. Do not claim success you did not observe.
5. **Ask before** anything destructive or hard to reverse: dropping or altering tables, deleting files you did not create, adding infrastructure, changing the auth or role model, or touching git history.
6. Do not create README or other documentation files unless asked. If a convention in this file changes, update this file in the same change.

### Testing against a database

PostgreSQL holds the user's real data. To test endpoints:
1. Create a throwaway database (e.g. `simrs_<feature>_test`) and start the app with `DB_NAME=<it>`.
2. Exercise the endpoints with `curl`.
3. Stop the server, drop the throwaway database, and delete any temporary files or binaries you created.

Never run write tests against the configured `DB_NAME`. Stop servers by PID (`ss -ltnp | grep :8080`), not `pkill -f <pattern>`, which can kill your own shell. If PostgreSQL is not running, say so; do not try to work around it.

## Project structure

```
cmd/app/                 entry point only
internal/
  app/                   composition root: migrate, seed, wire services, mount routes
  features/<feature>/    one folder per business feature (auth, roles, users, ...)
  platform/
    config/              env loading and Validate()
    database/            PostgreSQL connection
    middleware/          Gin middleware (auth, security headers, CORS)
    models/              ALL GORM models, one file per model (roles, users, patients, ...)
    utils/               helpers shared by many features (responses, params, pagination, token)
pkg/swagger/             Swagger general info + UI registration
docs/                    generated by swag; never edit by hand
```

- Business logic lives in `internal/features/<feature>/`, never in `cmd/`, `app/`, or `platform/`.
- **Every GORM model lives in `internal/platform/models/`**, never inside a feature, so a model can be shared without moving it later. Features reference them as `models.X`. Other code used by **one** feature stays in that feature; move it to `platform/` only when a second feature needs it.
- Do not add top-level folders without asking.
- A feature that handles several resources (e.g. `examinations`: vital signs and SOAP note) keeps them under one route root and prefixes files by sub-resource (`vital_*.go`, `soap_*.go`), with `<feature>_route.go` and the shared service/repository wiring in `<feature>_*.go`.

### Feature layout

```
<feature>_dto.go         request/response structs, validation tags, mapping
<feature>_repository.go  data access + sentinel errors
<feature>_service.go     business rules
<feature>_handler.go     HTTP handlers + Swagger annotations
<feature>_route.go       RegisterRoutes(rg, handler, middlewares...)
```

Dependencies flow one way: `route → handler → service → repository → database`.

- **Handler**: bind and validate input, call the service, map errors to status codes in a `fail` method. No business rules, no GORM.
- **Service**: business rules and orchestration. No `gin` import, no HTTP status codes.
- **Repository**: the only layer using `*gorm.DB`, always via `db.WithContext(ctx)`. Translate `gorm.ErrRecordNotFound`, `ErrDuplicatedKey`, and `ErrForeignKeyViolated` into the feature's sentinel errors.
- Services and repositories are interfaces built by `NewService` / `NewRepository`; `NewHandler` returns `*Handler`.
- To use another feature, depend on a small interface declared by the consumer (e.g. `RoleFinder`). Never import another feature's repository or handler. Avoid import cycles.
- Take `ctx` from `c.Request.Context()` and pass it down. Never use `context.Background()` inside a request.

## Code style

- **Everything is in English**: identifiers, comments, logs, error and API messages, Swagger text, commits. Reply to the user in the language they use.
- `gofmt` formatting; idiomatic Go; match the surrounding code (naming, comment density, structure).
- Packages are lowercase and match their folder; files are `<feature>_<layer>.go`.
- Wrap errors with `fmt.Errorf("doing x: %w", err)`; compare with `errors.Is`. Sentinels are package-level `var ErrX = errors.New("lowercase message")`.
- Comments explain **why**, not what. No doc comments on exported names unless behavior is non-obvious. No commented-out code.
- Small, single-purpose functions. No dead code, unused parameters, or unused exports.
- No global mutable state; inject dependencies through constructors.
- Add a dependency only when needed, then `go mod tidy`.

## API conventions

- Base path `/api/v1/<resource>`; resources are plural and lowercase.
- Methods: `GET` list/detail · `POST` create (`201`) · `PUT` update editable fields · `PATCH` single-field or state change (`/role`, `/status`) · `DELETE` and password reset return `200` with `data: null`.
- **IDs are UUIDs.** Parse path IDs with `utils.ParseUUIDParam` (bad UUID → `400`, unknown → `404`).
- Status codes: `400` invalid input · `401` unauthenticated · `403` not allowed · `404` not found · `409` duplicate or in use · `500` unexpected.
- **Every response uses the envelope** `{success, message, data}`. Send success with `utils.Success(c, status, message, data)` and failures with `utils.AbortWithError(c, status, message)` (`success: false`, `data: null`). Never call `c.JSON` / `c.Status` directly in handlers. Messages are English, e.g. `"User updated successfully"`.
- Map unknown errors to `500 "internal server error"`; never expose raw database errors.
- List endpoints are paginated with `utils.ParsePagination` (`page`, `limit`, max 100) and respond with `utils.SuccessPaginated(c, message, data, utils.NewPagination(page, limit, total))`, which adds `pagination` (`current_page`, `items_per_page`, `total_items`, `total_pages`, `has_prev_page`, `has_next_page`, `prev_page`, `next_page`) beside `data`. Escape `LIKE` wildcards in search input.
Response shapes (`data` is `null` when there is nothing to return; `pagination` only on lists):

```json
{ "success": true, "message": "User retrieved successfully", "data": { } }

{ "success": true, "message": "Users retrieved successfully",
  "pagination": { "current_page": 1, "items_per_page": 20, "total_items": 42, "total_pages": 3,
                  "has_prev_page": false, "has_next_page": true, "prev_page": null, "next_page": 2 },
  "data": [ ] }

{ "success": false, "message": "user not found", "data": null }
```

Defaults: `page=1`, `limit=20` (max 100). `prev_page` / `next_page` are `null` at the first / last page.

- Never return `PasswordHash` or other secrets. Use response DTOs, not raw GORM models, for models with sensitive fields (User always).
- Request DTOs use `binding` tags with sensible `max` lengths. Normalize input in the service (trim; lowercase emails).

## Database

- Connection comes from `DB_*` env vars. Never hard-code credentials or DSNs.
- GORM runs with `TranslateError: true`; rely on `gorm.ErrDuplicatedKey` and similar.
- Schema is managed by `AutoMigrate` in `internal/app/migrate.go`. Register new models there, referenced tables first. That file holds only permanent, idempotent startup steps (sequences, expression indexes, derived-data repair).
- **One-off or cleanup SQL** (data fixes, backfills, dropping unused columns or tables) never goes into a file, migration, or Go code. Give the exact SQL in your reply so the user runs it by hand, and do not commit it.
- Primary keys are UUIDs: `gorm:"type:uuid;primaryKey;default:gen_random_uuid()"`.
- `AutoMigrate` cannot change a column's type. Tell the user a manual migration is needed. **Never drop or reset the user's tables without explicit confirmation.**
- Seeds must be idempotent (`OnConflict`).
- Use parameterized queries only (`Where("x = ?", v)`); never concatenate SQL.

## Security

- `middleware.SecurityHeaders()` stays registered globally. API responses get the strict CSP; only `/swagger` gets the relaxed one.
- `middleware.CORS` is registered only when `CORS_ALLOWED_ORIGINS` is set. Origins are an explicit allow-list; **wildcard `*` is forbidden** (`Config.Validate()` rejects it). Credentials are not allowed. Never reflect `Origin` unchecked.
- Every endpoint requires `Required` plus an explicit `RequireRoles(...)`, except the intentionally public ones: `/ping`, `/auth/login`, `/swagger`, `/display/queues` (waiting-room screens; it must never expose patient data), and `/apm/*` (self-service registration kiosk).
- `/apm/*` has no login, so it stays minimal: rate limited per IP (`middleware.RateLimit`, strict on patient lookup), returns only the brief fields a kiosk needs (never contact, address, allergies or NIK), is read-only except creating a patient and registering a visit for **today**, both through their own services (no other date, no approval), and exposes no license or account data. Widen it only after asking.
- Never log or print secrets, tokens, passwords, or hashes.
- Never commit `.env`. Every new env var goes into `.env.example` (placeholder value) and `internal/platform/config`; validate required or unsafe values in `Config.Validate()`.
- Do not weaken validation, CSP, auth, or ownership checks to make a test or demo pass.

## File upload

- Files use **presigned URLs to MinIO**: the client asks `POST /files/uploads`, PUTs the bytes straight to storage, then calls `POST /files/{id}/complete`; downloads go through `GET /files/{id}/download-url`. The API never carries file bytes. The storage sits behind `storage.ObjectStorage` (`platform/storage`).
- File upload is **optional**: it is off while `MINIO_ENDPOINT` is empty. `MINIO_PUBLIC_ENDPOINT` must be an address the browser can open, because presigned URLs are signed for that host.
- The `files` feature is generic. A feature gets attachments by implementing `files.Target` (resource type, roles, allowed types, size and count limits, `Authorize`) and passing it to `mountFiles` in `internal/app/files.go`. Do not add file logic to the owning feature; do not import `files` from it (it only needs the methods).
- Never trust the client's content type: `Complete` checks the stored size and the real leading bytes. Only allow types `http.DetectContentType` can recognize.

## Swagger

- General info lives only in `pkg/swagger/swagger.go`; handler docs are annotations directly above each handler. Regenerate with `make swagger`.
- Every handler needs: `@Summary`, `@Description` (state the required role), `@Tags <feature>`, `@Accept`/`@Produce`, every `@Param`, `@Success`, every possible `@Failure` (`{object} utils.ErrorResponse`), `@Router`, and **`@Security BearerAuth` on protected endpoints**.
- DTO fields carry `example:"..."` tags; `uuid.UUID` fields also need `swaggertype:"string"`.
- Swag cannot parse generic types. Document success with the field-override syntax: `{object} utils.Response{data=Role}`, `{object} utils.Response{data=[]Role}`, `{object} utils.PaginatedResponse{data=[]Response}`, or plain `utils.Response` when `data` is null.
- Authorize in Swagger UI expects `Bearer {token}`.
